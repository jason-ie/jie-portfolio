What the sample actually does, concretely:
- Opens with a clear stated thesis/position, often as "I believe X because Y" or a flat claim, not a hook.
- Willing to be funny and irreverent. Snark and humor are load-bearing, not decoration.
- Uses parenthetical asides in italics for a quick aside/joke/objection-and-dismissal ("(what about hamartia, Zeus?)", "(clearly, very neat)") — a quick voice-in-the-margin, not a full digression.
- Direct address to the reader is allowed and used deliberately: "Hear me out:", "Anyway, if you stuck around to read this far,..." This breaks the fourth wall on purpose, unlike the old rule against addressing the reader.
- Structures arguments as an explicit numbered/enumerated list embedded inside prose, each point a self-contained mini-paragraph.
- Mixes elevated/precise vocabulary ("ecstatic celebration," "divine outcast," "relentless defiance") with casual, punchy phrasing ("flip the bird at the gods," "spare me"). The contrast between register is intentional, not sloppy.
- Rhetorical questions ARE used, sparingly, for emphasis at the end of a paragraph ("Is it how it should be?") — reverses the old "no rhetorical questions" rule.
- Closes with a punchy, quotable, memorable line — the old rule banning aphoristic closers is reversed here; the closer IS the point.
- Willing to add a creative flourish beyond straight argument — e.g. an invented dialogue scene — as a coda that dramatizes the thesis rather than just restating it. Not required for short answers, but shows the ceiling of the voice.
- Confident, sometimes combative stance — picks a side and argues it, doesn't hedge or both-sides it.

How to apply to job application answers: still ground everything in real facts about Jason (no fabrication — this rule never changes, see the Hyperliquid correction). But deliver those facts with a stated position, willingness to be a little funny/direct, and a memorable closing line, rather than the flatter, quieter, "sincere plain declarative" register used before. Scale down the numbered-list and invented-dialogue devices for short-word-count answers (under ~150 words), but keep the thesis-first structure, the confident stance, and a punchy closer.

## macOS notification click target can't be redirected via AppleScript (2026-08-17)
- Claude Code hook notifications posted with `osascript -e 'display notification ...'` are attributed to Script Editor, so clicking one opens Script Editor. Wrapping the call as `tell application "iTerm2" to display notification ...` does NOT change this — `display notification` executes in osascript's own process regardless of the tell target, and osascript's bundle identity is Script Editor. I shipped that fix and it failed in a fresh session.
- Second failed fix: `terminal-notifier -activate com.googlecode.iterm2`. It exits 0 but macOS never registers `fr.julienxx.oss.terminal-notifier` in Notification Center (`defaults read com.apple.ncprefs apps` shows nothing), so every banner is silently dropped. v2.0.0 is broken on current macOS; `lsregister -f` does not fix it. Its `-sender` flag also hangs forever.
- Hooks are spawned with NO controlling terminal (`tty` returns "not a tty", `/dev/tty` is "device not configured"), so a hook can never post an iTerm-native notification via the OSC 9 escape sequence either.
- Third failed fix: `"preferredNotifChannel": "iterm2"`. iTerm2 does not render OSC 9 notifications on this machine at all (verified by writing the escape sequence directly to the session tty — nothing appeared, while a Script Editor notification sent at the same instant did). So the built-in iTerm channel is dead here too.
- Fourth failed fix: custom AppleScript applet (`osacompile` + hand-set CFBundleIdentifier + ad-hoc `codesign -s -`). THE KEY FINDING: macOS delivers exactly ONE notification from a never-before-seen bundle id, then silently drops all later posts from that app. Verified across three separate bundle ids — each showed its first banner, then went permanently silent. Location (`~/.claude`, `~/Applications`, `/Applications`), `lsregister -f`, keeping the app alive after posting, and the System Settings "Allow notifications" toggle all made no difference. The toggle is cosmetic for ad-hoc-signed apps.
- CONCLUSION: on this machine, Script Editor (via plain `osascript`) is the ONLY sender whose notifications reliably display, and a notification's click target is owned by the posting app and cannot be redirected. Therefore "notify me AND take me to the iTerm session on click" is NOT achievable without a properly signed app (Apple Developer ID, $99/yr). Final state = the original Script Editor hooks, unchanged. Do not re-attempt terminal-notifier, OSC 9, preferredNotifChannel, or homemade applets — all four are ruled out by direct test.
- Process lessons: (1) exit code 0 from a notification command proves nothing — not that it displayed, not where the click lands. Only the user seeing/clicking it verifies that. (2) BEFORE building anything, check the OS-level prerequisites the user controls: System Settings → Notifications enablement and Focus/DND. The user's notifications were simply switched off during part of this, which invalidated several tests and sent me chasing phantom bugs. (3) I shipped three fixes on exit-0 alone and walked back all three; when the success signal cannot reach me, say the check is unverified and ask, rather than declaring it done. (4) When a hypothesis "confirms" (fresh bundle id worked), check whether a simpler rule explains it (first-post-only) before building on it — I mistook a one-shot allowance for a fix twice. (5) Biggest one: the structural fact that killed this (click target belongs to the posting app) was knowable in the first five minutes. State the hard constraint up front and let the user decide whether workarounds are worth their time, instead of burning an hour discovering it empirically.
